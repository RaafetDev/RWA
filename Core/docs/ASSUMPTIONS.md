# RitaWapp v1.0.1 - Specification Assumptions and Resolutions

This document records all architectural decisions and resolutions applied to
ambiguous or conflicting specifications.

| Topic                                 | Resolution & Implementation Details                                                                                                                                                                                                                                                                                                                                           |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Module Count**                      | Exactly 18 modules: `fs`, `os`, `path`, `process`, `shell`, `appWindow` (alias `webUI`), `network`, `database`, `update`, `cloudSync`, `tray`, `net`, `dgram`, `http` (with `https`), `fetch`, `express`, `admZip`, `ws`. All module counts in documentation and tests are dynamically derived from `registry.ts`.                                                            |
| **Directory Layout**                  | Strict `Core/`-only layout. Functional root contains only `Core/`, `RitaWapp.ts`, `mod.ts`, and `deno.json`. `rwa.cmd` is authored in `Core/cli/bin/rwa.cmd` and installed to `%LOCALAPPDATA%\RitaWapp\bin\`.                                                                                                                                                                 |
| **Toolchain & Frontend Bundler**      | Strictly Deno-native. esbuild/deno bundling is used without requiring Node.js or npm packages. Vue 3 runtime is bundled/vendored cleanly. Node-only packages and `npm:` specifiers are completely forbidden.                                                                                                                                                                  |
| **Cipher & Bundle Storage**           | AES-256-GCM authenticated encryption is used for all asset bundles (`Rita.W.app`). Nonce (96-bit) and tag (128-bit) are verified in RAM before decompression or WebUI serving. No plaintext files are ever extracted to disk.                                                                                                                                                 |
| **DevTools Security Policy**          | DevTools and debugging context menus are strictly gated. In release builds (`rwa build`, `packed`, `release`), DevTools are disabled and omitted from compilation (`-DRITAWAPP_DEV` is omitted). `--devtools` is only accepted if compiled with dev support.                                                                                                                  |
| **Tray Flags**                        | Canonical flag is `tray.enable`. Legacy aliases `trayEnable` and `trayEnabel` are supported with deprecation warnings.                                                                                                                                                                                                                                                        |
| **Assets Mode**                       | Canonical flag is `assetsMod`. Alias `assetsMode` is supported. When enabled, media and binary assets reside in `data/assets/` while code assets remain encrypted in `Rita.W.app`.                                                                                                                                                                                            |
| **AES Key Generation**                | Each new project generated via `init` generates a unique 256-bit (64 hex character) AES key. Keys are never committed to version control. Bundle encryption provides confidentiality against casual inspection.                                                                                                                                                               |
| **Update Verification**               | Automatic updates verify the SHA-256 manifest hash before staging or replacing files. Atomic swap maintains a rollback copy of the previous executable.                                                                                                                                                                                                                       |
| **wsApi Protocol**                    | JSON-RPC 2.0 over WebSocket at port 19800 by default (binds to loopback `127.0.0.1`). Requires token authentication unless explicitly disabled with `--no-auth`. Supports headless native host routing for background services.                                                                                                                                               |
| **Consumer Project Resolution**       | `getFrameworkRoot()` accurately derives framework root via `RWA_ROOT`, `%LOCALAPPDATA%\RitaWapp\bin\rwa.root`, or `import.meta.url` traversal. Consumer apps created anywhere link against framework C sources while generating per-project `.dev/app_credentials.h` and binaries in their own directory.                                                                     |
| **Interactive Wizard & Config**       | Uses `jsr:@cliffy/prompt` (Deno-native JSR, zero Node/npm). Projects are scaffolded with pure `RitaWapp.json` (also supporting `RitaWapp.config.ts`), containing only template code, RPC bridge, and config.                                                                                                                                                                  |
| **Smart Dev Server & Reload**         | `rwa dev` file watcher separates frontend asset modification (serves dynamically via local Deno HTTP server with WebSocket live-reload) from C/native and config modifications (recompiles binary and relaunches runtime process). Dev mode never bundles or encrypts to disk; only `rwa build` produces `Rita.W.app`.                                                        |
| **GNU Linker Unicode Safety**         | MinGW GNU `ld.exe` fails with non-ANSI / Arabic directory names on Windows. `compileProject` links binaries to an intermediate ASCII scratch path in `.dev/` before copying to the destination folder using Unicode Win32 `CopyFileW` (`Deno.copyFile`).                                                                                                                      |
| **Canonical Module Registration**     | 19 canonical modules are linked and registered: 15 native C modules, 3 pure TS modules (`path`, `fetch`, `express`), and `mongoose-sqlite` (Mongoose ODM layer backed by embedded SQLite JSON engine). Aliases (`db`, `sqlite`, `zip`, `https`, `websocket`, `webUI`, `mongoose_sqlite`) are dispatched transparently through canonical module handlers.                      |
| **Zero-Residue Production Packaging** | In release builds (`rwa build`), no `.rwa` directory or `webui_port` file is generated (dev-only). SQLite temp directory (`sqlite3_temp_directory`) is redirected to Windows `%TEMP%`. On application shutdown, `sqlite3_wal_checkpoint_v2` truncates the WAL log, and any remaining `-wal`/`-shm` auxiliary files are deleted, leaving only the clean primary database file. |
| **Automated Self-Test Harness**       | `--rwa-selftest` inspects live window HWND, pings WebUI, records registered modules, saves screenshot via BitBlt to `.rwa/selftest.png`, and writes `.rwa/selftest.json`. All modal `MessageBox` calls are suppressed in automated selftest mode to prevent headless test hangs.                                                                                              |
